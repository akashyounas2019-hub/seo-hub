# Product

## Register

product

## Users

Solo operator + a small student labor pool running a network of local cleaning-business client websites and the leads/tasks/SEO/payments work behind them. Primary user is the admin (full visibility), with managers and students scoped to assigned sites. Used during real work sessions at a desk — triaging leads, managing tasks, reviewing site QA, running the website-build pipeline — not a casual browsing context.

## Product Purpose

An operator console (the "AI Website Factory" / GYL Platform) that researches, designs, builds, and operates local-service-business websites end to end: lead capture, task management, AI-assisted site building (design research → keyword research → content → site builder studio), QA, SEO tracking, and (per later phases) payments and call tracking. Success looks like an operator moving fast across many sites/tasks without losing track of what needs attention.

## Brand Personality

Clear, calm, efficient. Friendly enough to not feel like enterprise software, but still trustworthy and precise — this is a tool people rely on to run a real business, not a consumer app. Three words: approachable, organized, fast.

## Anti-references

No specific anti-references named by the user. Avoid: dense, low-contrast "dashboard-as-spreadsheet" tools; anything that reads as a marketing/landing page rather than a working tool; gratuitous decoration that slows down scanning a list of leads/tasks.

## Design Principles

- Scannability over decoration — this is used to triage lists (leads, tasks, QA results) quickly; hierarchy and contrast matter more than visual flourish.
- Full-text navigation, not icon-guessing — the operator and student labor pool should never have to hover to find out what a sidebar icon means.
- Group by real workflow, not alphabetically — sidebar structure should mirror how the operator actually thinks about the product (build a site vs. run SEO vs. manage the team), not an arbitrary list.
- Light, friendly, still serious — approachable SaaS feel is fine; the tool still needs to read as dependable for running a real business.
- Don't relitigate scope per task — only the parts of the UI actually touched by a given request should change; this is a living admin tool, not a one-shot redesign.

## Accessibility & Inclusion

Standard WCAG AA contrast (body text ≥4.5:1, large/bold text ≥3:1). No additional stated requirements — design colorblind-safe accents as good practice (don't rely on hue alone for status/severity signals already in the product, e.g. QA pass/warn/fail).
